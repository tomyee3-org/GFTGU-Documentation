Start here

A shell made of many small masses should pull like one mass at its centre when you stand outside, and give no net pull when you stand inside. Run the commands below in order from the SphereGravity program folder. Each run prints a comparison table and opens a graph; close the graph to finish the run. Python 3.10 or later, NumPy and Matplotlib are required.

The shell radius and gravitational constant are both 1 in the program's dimensionless units. The numerical result is a midpoint sum, so the small deviations from Newton's exact shell theorem are part of the lesson. The point at the shell surface, r = 1, is excluded because the ideal thin shell's field jumps there.

The equations use MathJax from an online service; the program runs without an internet connection. This page moves from the figure and printed result to the equation. Try each question before reading on.

Beat 0 · Outside it looks like a point

Begin with the pull itself, not the error scale.

python main.py --outputType acceleration --nDiv 100 --epsilon 0.001 --radii 0.5 0.995 1.005 2 3 4 5

Compare the printed predicted g and expected g at r = 0.5, 2 and 4. The pull is almost zero inside and falls by about a factor of four between 2 and 4. The line has a gap at the dashed shell boundary.

Try next. If you double the outside radius again, what pull do you expect relative to that at 4? Check with python main.py --radii 4 8; this changes the table's radii but leaves the graph's radius grid alone.

The continuum rule is \(g(r)=0\) for \(r<1\), and \(g(r)=M/r^2\) for \(r>1\). With mass per unit area \(\varepsilon=0.001\), \(M=4\pi\varepsilon\). The small nonzero interior number comes from the finite tile sum.

Beat 1 · Make the tiles coarse

For comparison, the default settings are --nDiv 100.

python main.py --nDiv 10 --outputType relative_difference

The program uses ten divisions in each angular direction. Look at numerical midpoint mass, continuum mass, and latitude step h = pi/nDiv. The numerical mass is slightly high; compared with Beat 0, its fractional error grows about a hundredfold.

Try next. Which part of the graph changes most as you coarsen the tiles? Compare the two sides of the dashed line rather than just the far right of the plot.

The midpoint latitudes are \(\theta_k=-\pi/2+(k+1/2)h\), \(h=\pi/n\). Their summed mass is \(M_{\rm num}=4\pi\varepsilon\,(h/2)/\sin(h/2)\); thus \(M_{\rm num}/M-1\approx h^2/24\) for fine tiles. The latitude bands are approximated, not integrated exactly.

Beat 2 · Keep moving outward

python main.py --radii 2 5 10 100 1000

Follow the printed relative difference as distance grows. It approaches the small excess in the tile mass rather than zero. The graph did not change: --radii selects table entries, while the graph still stops at 4.995.

Try next. At a very large radius, which mass does the tiled shell act like: the exact smooth-shell mass or the sum of its tile masses?

Far away, \(g_{\rm num}\simeq M_{\rm num}/r^2\). The table compares against \(M/r^2\), so its relative difference tends to \(M_{\rm num}/M-1\). Beat 6 asks why the graph's normalization gives a different far-field limit.

Beat 3 · Walk from the centre to the wall

python main.py --radii 0 0.25 0.5 0.75 0.9

The table's expected g is zero throughout. Consequently it reports undefined; g/M= in place of a relative difference. The residual becomes harder to ignore close to the shell.

Try next. Why can the program divide an interior pull by the shell mass, but not call the answer a relative error? Near r = 0.9, zoom in vertically before using the cursor to inspect the interior residual, then compare it with the table. At the default scale most interior residuals are smaller than one screen pixel.

In the continuum, the near and far patches within the same narrow cone have equal and opposite axial pulls. Finite midpoint tiles do not pair exactly, so the residual is a numerical error; division by a zero expected pull would be undefined.

Beat 4 · Refine by ten

For comparison, the default settings are --nDiv 100.

python main.py --nDiv 1000 --radii 0.5 0.995 1.005 2 3 4 5
python main.py --nDiv 10000 --radii 0.5 0.995 1.005 2 3 4 5

Compare the mass error and the table's error at a fixed radius with the earlier 100-division run. These long runs refine the graph's full 1000-point profile as well as the short printed table; the 10000-division run can take tens of seconds.

Try next. Record the table's r = 2 relative difference for 100, 1000 and 10000 divisions. Does each tenfold refinement make it about ten times or a hundred times smaller?

The leading midpoint error scales like \(h^2\), and \(h=\pi/n\). The h^2 estimate is calculated from a formula independently of the tile sum; an unmarked row is an opportunity to compare the two.

Beat 5 · Approach the surface

python main.py --radii 0.995 1.005 1.01 1.05 1.1 --nDiv 100
python main.py --nDiv 10000 --radii 0.995 1.005 1.01 1.05 1.1

At 100 divisions every row except r = 1.1 has a *: the error estimate there is unreliable and can even have the wrong sign. At 10000 divisions, the marks disappear and the estimate approaches the measured error. Compare the pulls at 0.995 and 1.005 in the fine run.

Try next. The fine run samples on opposite sides, but does not sample exactly at the surface. Predict the limiting jump, and explain why their finite-distance difference is a little smaller.

The continuum shell's magnitude rises from zero just inside to \(4\pi G\varepsilon\) just outside. For a general surface layer, it is the signed normal component of the field that has this universal jump; the magnitude statement here uses spherical symmetry. The program marks an estimate when \(h\geq\tfrac12\min(1,|r-1|)\); an unmarked row near the cutoff still calls for caution.

Beat 6 · Read the error plot

python main.py --nDiv 100 --outputType relative_difference

The default graph plots relative_difference. The tall pair of spikes beside r = 1 sets its vertical scale. At the default scale the curve at r = 2 is less than one screen pixel above zero, so the cursor cannot read its value. Use the toolbar magnifier to zoom repeatedly around r = 2, first selecting approximately 0 to 1e-4 on the vertical axis. Even then the cursor gives only about one significant figure. The plotted value is 5.03e-05; the table prints 9.1423e-05. Compare those numbers using the formula below.

Try next. The table uses the exact mass \(M\), while the plot uses the tile mass \(M_{\rm num}\). Which view isolates the error in the shape of the field? Why does the plotted far-field error tend to zero?

Outside, if \(\delta_{\rm table}=g_{\rm num}/(M/r^2)-1\), then \(\delta_{\rm plot}=(1+\delta_{\rm table})/(M_{\rm num}/M)-1\). Inside, the displayed residual is \(g_{\rm num}/M_{\rm num}\), while the table prints \(g_{\rm num}/M\). Do not apply the exterior subtraction to an interior row.

Beat 7 · Double the mass per area

For comparison, the default settings are --epsilon 0.001.

python main.py --epsilon 0.002 --outputType acceleration --nDiv 100

Compare the graph and mass lines with Beat 0. The masses and pulls double; the graph's shape, shell location and the relative errors do not. --epsilon sets mass per unit area, not a geometric shell thickness.

Try next. Run python main.py --epsilon 0.002. Why is the relative-difference graph unchanged even though the acceleration graph doubles?

Every tile mass is proportional to \(\varepsilon\), and so is each summed pull. A ratio of a pull to a comparison pull from the same shell cancels \(\varepsilon\).

Beat 8 · Break the approximation

For comparison, the default settings are --nDiv 100.

python main.py --nDiv 1
python main.py --radii 1
python main.py --nDiv 100001

The first run collapses the shell to an equatorial ring: its inside field no longer resembles zero and all error estimates are marked. The next two commands are deliberately rejected: the ideal surface is discontinuous and the division count is capped at 100000.

Try next. Use python main.py --nDiv 2, then 10 and 100. At which radii does the ring picture start to resemble the shell? Which marked rows remain a poor basis for extrapolation?

This is a convergence experiment, not a promise that every finite tiling is accurate. The exact theorem applies to the smooth uniform sphere, not to one ring.

Parameters at the terminal

All settings are command-line options in main.py. Use python main.py --help for the parser's live descriptions or python main.py --version for the current stamp. --radii affects only the table; --outputType affects only the plot.

OptionDefaultMeaning
--nDiv100Number of angular divisions in each direction; an integer from 1 through 100000.
--outputTyperelative_differenceacceleration plots the raw pull; relative_difference plots its mass-normalized deviation.
--epsilon0.001Positive mass per area in dimensionless units, from 1e-100 to 1e100; scales mass and acceleration.
--radii0.5 0.995 1.005 2 3 4 5One or more table radii, nonnegative and at most 1e100, excluding 1.

Where to trust the result

  • The ideal shell has zero thickness and radius 1. Its field is only calculated on one symmetry axis.
  • The numerical profile uses 1000 fixed radii from 0 to 4.995. The value at 1 is a placeholder, omitted from the drawn curve; the table rejects radius 1.
  • Near the shell, a tile can be larger than its distance to the test point. The * warns when the leading error estimate should not be used, but absence of a mark is not a rigorous accuracy guarantee.
  • The table compares to the continuum mass. The relative-difference plot compares to the tiled mass. An interior relative difference from zero is undefined, so the program shows a mass-normalized residual there.
  • The plot uses the explicit latitude loops and may be slow for large --nDiv. The model is Newtonian and dimensionless.
