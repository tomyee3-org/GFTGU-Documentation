Known Limitations

  • Ideal zero-thickness shell of radius 1, in dimensionless Newtonian units with G = 1. Epsilon scales mass; the field is computed only on a symmetry axis.
  • At r = 1 the field is discontinuous; the table rejects that radius and the plotted profile omits its finite placeholder. The fixed graph grid runs from 0 to 4.995.
  • Coarse tiling is inaccurate beside the shell. A starred error estimate is outside its intended regime; an unmarked row near the marking threshold is not a rigorous accuracy guarantee.
  • The table uses continuum mass, the plot uses tiled mass. Relative error from an interior exact field of zero is undefined; the displayed interior quantity is a mass-normalized residual.
  • Inputs are limited to 1 through 100000 divisions, epsilon from 1e-100 to 1e100, and table radii up to 1e100. The explicit profile loops may take tens of seconds for large division counts.
  • The module demonstrates one thin shell, rather than integrating an arbitrary spherical density profile. SG1 explains the physical extension.
  • Help equations require online MathJax; the program and embedded guide images work offline.

  • Build identification reports unknown when a core source file cannot be read. Runtime type annotations remain conservative.

Open Bugs

  • OB-1 (P3; Codex Audit 22 item 1). Beat 5 of SphereGravity-claude.html says that the jump across a surface layer is 4πGε “whatever the shape of a surface layer”, which is true of the signed normal component of the field but not of its magnitude.
    Reproduction: read the sentence after Eq. (15) in Beat 5. Observed: the magnitude jump of Eq. (15) is stated for a surface layer of any shape. Expected: for a general layer only the signed normal component jumps by 4πGε (an infinite uniform sheet has the same magnitude, 2πGε, on both sides).
  • OB-2 (P3; Codex Audit 22 item 2). The paragraph after Eq. 7 of SphereGravity-original.html calls Mnum “the pull just outside the surface”, but the tiled pull just outside the surface is different.
    Reproduction: python main.py --radii 1.00000000001. Observed: predicted g 0.0062832, about half of numerical midpoint mass 0.012567. Expected: the text describes Mnum as the point-mass reference pull at r = 1, not as the pull of the tiles.

Major Improvements in This Release

Version 1.4.0, build 217c2c26a44a (Audit 21 response, and a Help change after Audit 22):

  • Radius labels in the comparison table give back the radius exactly; --radii 0.99999999999 1.00000000001 prints those two labels instead of 1 and 1. Usual radii keep their short labels.
  • The Beats Help gives separate exterior and interior relations between the plotted and the printed relative differences (Eq. (17)), and the Reference Guide's Eq. 7 shows that the plot divides by the tiles' mass Mnum, while the table divides by the exact mass 4πε.
  • After Audit 22, the Related Programs sections of both Help files name the related programs without links to their Help files and without chapter numbers. The program and its build did not change.

Version 1.4.0, build a43a939a4607 (Kickoff2, not released separately):

  • New Beats tutorial Help, SphereGravity-claude.html, with nine beats, 19 equations and 11 experiments. The Reference Guide Help is retained, kept current, as SphereGravity-original.html.
  • New option --radii R [R ...] chooses the comparison radii; the default is the seven radii of 1.3.0.
  • The table prints a new line, latitude step h = pi/nDiv, and a new column, h^2 estimate, from the new public function midpoint_error_estimate(). A row is marked *, with a footnote, where the estimate does not apply. The values printed by 1.3.0 are unchanged.
  • The note about the undefined interior relative difference is printed only when the table has an interior row.
  • --epsilon accepts 1e-100 to 1e100 and --radii accepts radii up to 1e100; values outside these ranges are rejected. In 1.3.0, --epsilon 1e308 ended with a traceback and --epsilon 1e-320 printed a predicted g of 0 at r = 4 and 5.
  • plot_spheregravity() returns the Matplotlib figure and axes, so the plot can be saved.

Known Limitations

  • An ideal thin shell of radius 1 in dimensionless units (G = 1); ε sets only the mass per unit area.
  • The field is computed on the symmetry axis, with each latitude treated as a uniform ring, whatever the number of divisions.
  • The field is discontinuous at r = 1; that point is left out of the plot, and --radii 1 is rejected.
  • The tiling is least accurate beside the shell; the h2 estimate does not apply to rows marked *.
  • Inside the shell a relative difference is undefined, and the table prints g/M instead.
  • The plot divides by the tiles' mass and the table by the exact mass, so their exterior values differ.
  • Inputs are limited to 1 to 100000 divisions, ε from 1e-100 to 1e100, and radii up to 1e100.
  • The plotted profile uses the explicit textbook loops; a 10000-division run takes about ten seconds.
  • The equations in the Help are typeset by MathJax and need an internet connection.

Known Minor Maintenance Items

  • A NumPy float32 value of ε passed to the physics functions emits a RuntimeWarning, although it is accepted or rejected correctly (Grok, Audit 22).
  • The build identifier reads unknown when a core file is missing.
  • Runtime type annotations are conservative.
  • The faster NumPy implementation is selected only by editing two lines of physics_spheregravity.py.
  • There is no command-line option to save the figure or the table to a file.
  • SphereGravity-claude.html and SphereGravity-original.html are both present, and neither is marked as the current Help.
