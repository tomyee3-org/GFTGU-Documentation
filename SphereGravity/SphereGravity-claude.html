Overview

SphereGravity tests one of Newton's most useful results, the shell theorem: a thin, uniform spherical shell pulls on anything outside it exactly as if all its mass sat at its centre, and pulls on nothing inside it at all. The program does not assume the theorem. It cuts the shell into small tiles, treats each tile as a point mass, adds up their pulls at many distances from the centre, and compares the total with the theorem.

Every run prints the shell's mass as the tiles add it up beside its exact value, and a table of the computed and expected pull at a set of radii, with the difference between them and a prediction of how large that difference should be. Then it plots the computed pull, or its relative difference from the pull the theorem gives for the tiles' own mass, from the centre out to five shell radii.

The spine of the lesson is one sentence: adding up the inverse-square pulls of the tiles of a thin shell gives no pull inside and the pull of a point mass outside, as Newton proved, and the small differences that remain are the error of the sum itself, which falls as the square of the tile size wherever the tiles are small compared with the distance to the shell, and which the program predicts in advance; next to the shell, where that condition fails, the sum needs far finer tiles. Each numbered section below is one beat: a short argument, a command whose printed summary or plot illustrates that argument, and then the equation that the printed numbers follow from.

Scope: SphereGravity is about the field of one thin shell. Atmosphere, Star and Neutron use the shell theorem, through the mass inside a radius, to build whole spherical bodies.
What this program is, and what it does not model. SphereGravity is a teaching model of Newtonian gravity in dimensionless units: the shell has radius 1, \(G=1\), and every tile lies exactly on the radius-1 sphere, so the shell has no thickness; the parameter --epsilon only sets how much mass it carries. The field is computed only at points on one axis through the centre, which is enough because the shell is symmetric. The result is a numerical sum, not the exact integral, so it carries an error that depends on the number of tiles; the program prints that error beside a prediction of it. At the shell itself, r = 1, the exact field jumps and the program does not evaluate it. Beats 4, 5 and 8 show where the numbers stop being trustworthy.
Reading this page. The equations on this page are rendered by MathJax, loaded from a public CDN, so an internet connection is needed to see them typeset; with no connection, the raw TeX source (e.g. \(GM/r^2\)) will show as plain text instead of a formula. How to read this page

Each numbered section below is one beat: a short argument in words, a command whose output illustrates it, and then the equation that the output follows from. Do them in order the first time. After that, any beat can be opened on its own.

The program's output is a consequence of its equations, so what a beat shows is the equations at work, not independent evidence that they are right. The outside checks the program offers are the exact continuum values it prints beside the tiled sum, the expected g and continuum mass, and the column h^2 estimate, which predicts the error of the sum from a formula rather than from the sum. Beats 1 to 5 compare the sum with them.

The program has no random numbers, so every command prints the numbers quoted here. Beat 0 shows the theorem at the default settings, Beat 1 the tiles and their mass, Beat 2 the far field and Beat 3 the interior. Beat 4 refines the tiles, Beat 5 goes close to the shell, Beat 6 reads the default plot, Beat 7 changes the mass, and Beat 8 collects the coarsest tilings and the inputs the program refuses.

Run every command from the program's folder. Each run prints a summary and then opens a plot window; close the window to end the program. Each beat names the lines of the summary to look at. All quantities are dimensionless: lengths in units of the shell radius, and accelerations in units in which \(G=1\).

What kind of statement is each equation? Each displayed equation in the beats carries a tag. A red LAW tag marks a law of nature that the model adopts and does not derive; Eq. (1) is the only one. A grey DEFINITION tag marks a quantity that is defined by a formula. A blue DERIVED tag marks a result that follows from the equations already stated. A violet ALGORITHM tag marks a rule of the calculation, which is a choice made by the program rather than physics: Eqs. (8), (14) and (19). The tags are there so that a law, a definition and a numerical rule are never mistaken for one another. Nineteen equations are numbered; a few unnumbered ones appear where they are needed.

Beat 0 · Nothing inside, a point outside

Run the program with its default tiling and plot the pull itself.

python main.py --outputType acceleration

Look at the plot, and at the columns predicted g and expected g of the table. predicted g is the program's sum over the tiles; expected g is Newton's shell theorem. Ignore the other columns until Beat 2.

Three tasks, in order. First, look inside the shell. At r = 0.5 the tiles pull with predicted g = -9.1945e-07, and the theorem expects 0; on the plot the curve lies flat on zero from the centre almost to r = 1. Then look outside. At r = 2 the sum gives 0.0031419 against the expected 0.0031416, and at r = 4 it gives 0.00078544 against 0.0007854; the pull at 2 is 4.000 times the pull at 4, and more than 3400 times the size of the tiny leftover at 0.5, which Beat 4 shows is an error of the sum. Then look at the shell. The plot rises sharply from about zero to about 0.012 across the dashed line at r = 1, where it has a gap; just inside the shell it dips slightly below zero, and just outside it overshoots to more than 0.012 before it falls. Beat 5 explains the dip and the overshoot. Say what would have to be true of the shell's pull for the pull outside to fall to a quarter when the distance doubles.

Then the law. Every tile pulls on a test mass with Newton's inverse-square force.

(1)
Newton's law of gravitation for a point mass LAW
\[ \mathbf g=-\frac{G\,m}{d^{2}}\,\hat{\mathbf d} . \]

Here \(m\) is the mass of the tile, \(d\) its distance from the test mass, and \(\hat{\mathbf d}\) the unit vector from the tile to the test mass; \(\mathbf g\) is the acceleration of the test mass, or the force on a unit test mass. Adding the pulls of all the pieces of a uniform thin shell of mass \(M\) and radius \(R\) exactly, as Newton did, gives the shell theorem.

(2)
The shell theorem DERIVED
\[ g(r)=\begin{cases}\dfrac{GM}{r^{2}}, & r>R,\\[6pt] 0, & r<R.\end{cases} \]

Here \(g\) is the magnitude of the pull towards the centre at distance \(r\) from it. In the program's units \(R=1\) and \(G=1\), so the expected pull outside is \(M/r^2\) and inside it is 0; these are the expected g column. The theorem is why a planet or a star pulls on things outside it as if all its mass were at its centre, and why the matter outside a radius does not matter for the pull at that radius. Beat 1 looks at how the program builds the shell.

Beat 1 · The shell as tiles

The program cuts the shell into a grid of tiles, --nDiv in latitude and --nDiv in longitude. Use very coarse tiles, ten by ten, so that the effect of the tiling is large.

python main.py --nDiv 10

Look at the three lines under Shell mass comparison, and at the line latitude step h = pi/nDiv.

Three tasks, in order. First, compare the masses. The tiles add up to numerical midpoint mass 0.012618, while the shell's exact mass is 0.012566; the relative difference is 0.0041242. Then compare with Beat 0, which used 100 tiles each way: its relative difference was 4.1125e-05, a hundred times smaller for ten times as many divisions, ten times finer in latitude. Then read the step: latitude step h = pi/nDiv is 0.31416 here, against 0.031416 in Beat 0. Say why the tiles should carry slightly more mass than the smooth shell, not less.

Then the tiles. Latitude \(\theta\) runs from \(-\pi/2\) at the south pole to \(+\pi/2\) at the north pole, and longitude \(\varphi\) round the equator.

(3)
The angular grid DEFINITION
\[ \Delta\varphi=\frac{2\pi}{n},\qquad h=\Delta\theta=\frac{\pi}{n},\qquad \theta_k=-\frac{\pi}{2}+\Bigl(k+\tfrac12\Bigr)h,\quad k=0,1,\dots,n-1 . \]

Here \(n\) is --nDiv. Each tile is represented by its midpoint, at latitude \(\theta_k\), and carries the mass of the patch of shell around it.

(4)
Tile mass and shell mass DEFINITION
\[ \delta m_k=\varepsilon\cos\theta_k\,h\,\Delta\varphi,\qquad M_{\rm num}=\sum_{k=0}^{n-1}n\,\delta m_k,\qquad M=4\pi\varepsilon . \]

The area of a patch is \(\cos\theta\,\Delta\theta\,\Delta\varphi\) on a sphere of radius 1, and \(\varepsilon\), --epsilon, is the mass per unit area. All \(n\) tiles at one latitude are the same, so the program adds each ring of \(n\) tiles at once. \(M_{\rm num}\) is numerical midpoint mass and \(M\) is continuum mass. The sum of the cosines at the midpoints can be done exactly.

(5)
The mass of the tiles DERIVED
\[ \frac{M_{\rm num}}{M}=\frac{h/2}{\sin(h/2)}\approx1+\frac{h^{2}}{24} . \]

For \(n=10\), \(h/2=\pi/20\) and \((\pi/20)/\sin(\pi/20)=1.0041242\), the printed difference; for \(n=100\) it is 1.0000411245. Across each latitude band the band's width, \(\cos\theta\), curves downwards on both sides of its value at the midpoint, so the midpoint value is slightly more than the band's average width, and each ring slightly overcounts its area. The error falls as \(h^2\), which is why ten times as many divisions made it a hundred times smaller. Beat 2 turns from the mass to the pull.

Beat 2 · Far away, a point of the tiled mass

Print the comparison at points farther and farther from the shell, from 2 to 1000 shell radii.

python main.py --radii 2 5 10 100 1000

Look at the relative difference column and compare it with the mass line relative difference above the table.

Three tasks, in order. First, read the column from top to bottom: 9.1423e-05, 4.6409e-05, 4.2379e-05, 4.1137e-05 and 4.1125e-05. The difference between the tiled sum and the theorem gets smaller as the test mass moves away, but it does not go to zero. Then compare the last value with the mass: the relative mass difference is also 4.1125e-05. Far away, the tiles pull almost exactly like a point carrying the tiles' own mass, which is too large by that fraction. Then compare with the column h^2 estimate, which is 9.1385e-05 at r = 2 and 4.1123e-05 at r = 1000. Say why the pull of the tiles must approach that of a point of mass \(M_{\rm num}\), not \(M\), however the tiles are arranged.

Then the sum. By symmetry the pull at a point on the axis through the centre points along the axis, so the program puts the test mass on the axis, at \(z=-r\), below the shell's centre. A tile at latitude \(\theta\) is at height \(z=\sin\theta\).

(6)
Distance from a tile to the test mass DERIVED
\[ d(\theta,r)=\sqrt{1+r^{2}+2r\sin\theta} . \]

All the tiles of one ring are at the same distance, and their sideways pulls cancel round the ring, so the program treats each ring as a whole and keeps only the component of its pull along the axis. That component is Eq. (1) times \((r+\sin\theta)/d\), the axial separation over the distance.

(7)
The pull of one ring DERIVED
\[ \delta g_k=n\,\frac{G\,\delta m_k\,(r+\sin\theta_k)}{d(\theta_k,r)^{3}} . \]

A positive \(\delta g_k\) points in the \(+z\) direction, which for the test mass at \(z=-r\) is towards the centre. The program adds the rings.

(8)
The tiled sum ALGORITHM
\[ g_{\rm num}(r)=\sum_{k=0}^{n-1}\delta g_k . \]

\(g_{\rm num}\) is predicted g, computed by compute_acceleration_at_radii() in physics_spheregravity.py; it is positive when it points towards the centre. It is a midpoint-rule approximation to the integral that gives Eq. (2). The table compares it with the theorem.

(9)
The printed comparison DEFINITION
\[ \delta(r)=\frac{g_{\rm num}(r)-M/r^{2}}{M/r^{2}}\quad(r>1),\qquad \frac{g_{\rm num}(r)}{M}\quad(r<1) . \]

\(\delta\) is relative difference. Inside the shell the expected pull is zero and a relative difference would divide by zero, so the program prints undefined and the pull divided by the mass, g/M, instead. Both use the exact mass \(M\). Far away, every tile is at almost the same distance \(r\), and the sum becomes the total mass over \(r^2\).

(10)
The far field DERIVED
\[ g_{\rm num}(r)\to\frac{M_{\rm num}}{r^{2}},\qquad \delta(r)\to\frac{M_{\rm num}}{M}-1\qquad(r\to\infty) . \]

So the relative difference far away is the mass error of Beat 1, 4.1125e-05, and what is left at smaller \(r\) is an error in the shape of the field, which falls off with distance. Beat 3 looks inside the shell.

Experiments that go with this beat: Experiment 2 in Suggested Experiments.

Beat 3 · Inside, the pulls cancel

Print the comparison at five points inside the shell, from the centre to nine tenths of the way to the shell.

python main.py --radii 0 0.25 0.5 0.75 0.9

Look at the predicted g column, at the g/M values in the relative difference column, and at h^2 estimate.

Three tasks, in order. First, read the centre: predicted g is 1.5217e-18, rounding error in a sum of terms each about \(10^{-4}\), and the estimate is 0. Then read outwards: g/M is -2.3403e-05 at r = 0.25, -7.3167e-05 at 0.5, -0.00032343 at 0.75 and -0.0021036 at 0.9. The pull is tiny everywhere inside but grows towards the shell, and it is negative, pointing away from the centre, towards the nearer part of the shell. Then compare with the estimate: -2.3395e-05, -7.3108e-05, -0.00032227 and -0.0020505. Say why the pulls of the near and far sides of the shell cancel, although the near side is much closer.

Then Newton's argument. Draw a thin double cone from the test point, in opposite directions. It cuts two small patches out of the shell, at distances \(d_1\) and \(d_2\).

(11)
Cancellation of opposite patches DERIVED
\[ \delta A_i=\frac{d_i^{2}\,\delta\Omega}{\cos\alpha},\qquad \frac{G\,\varepsilon\,\delta A_1}{d_1^{2}}=\frac{G\,\varepsilon\,\delta A_2}{d_2^{2}}=\frac{G\,\varepsilon\,\delta\Omega}{\cos\alpha} . \]

Here \(\delta\Omega\) is the solid angle of the cone and \(\alpha\) the angle between the cone's axis and the shell's normal, the radius, which is the same at both ends, because a chord of a sphere meets it at equal angles at its two ends. The patch that is twice as far away has four times the area and so four times the mass, and its pull is exactly as strong as that of the near patch, in the opposite direction. Every direction pairs off in this way, so the total is zero. The tiled sum does not pair off exactly: its tiles are not cut by cones from the test point. What is left is the error of the sum, and it is largest near the shell, where the nearest tiles are closest. Beat 4 shows how it shrinks.

Experiments that go with this beat: Experiment 5 and Experiment 10 in Suggested Experiments.

Beat 4 · Ten times the divisions, a hundredth of the error

This is Schutz's convergence test. Run the default comparison again with ten times and then a hundred times as many divisions. The second run takes noticeably longer, about ten seconds on the computer used to write this page, because it computes the plotted profile with ten thousand rings at each of a thousand radii.

python main.py --nDiv 1000
python main.py --nDiv 10000

Look at the relative difference and h^2 estimate columns at r = 0.5 and 2, in these two runs and in the run of Beat 0, and at the mass line relative difference.

Three tasks, in order. First, read r = 2: the relative difference is 9.1423e-05 with 100 divisions, 9.1386e-07 with 1000 and 9.1385e-09 with 10000. Then read r = 0.5: g/M is -7.3167e-05, -7.3109e-07 and -7.3108e-09. Each tenfold refinement divides the error by 100, and the mass error goes the same way, from 4.1125e-05 to 4.1123e-07 to 4.1123e-09. Then compare with the estimate: at r = 2 it is 9.1385e-05, 9.1385e-07 and 9.1385e-09, so with 1000 divisions it agrees with the error to four digits, and with 10000 to all five printed digits. Say what kind of formula for the error would make it fall exactly a hundredfold for every tenfold refinement.

Then why the error goes as \(h^2\). The ring sum of Eq. (8) is \(2\pi\varepsilon\) times a midpoint-rule sum \(h\sum_k f(\theta_k)\) with \(f(\theta)=\cos\theta\,(r+\sin\theta)/d(\theta,r)^3\), and the exact field is \(2\pi\varepsilon\) times the integral of \(f\). For a smooth \(f\), the error of the midpoint rule has a known leading term, from the Euler-Maclaurin formula.

(12)
Error of the midpoint rule DERIVED
\[ h\sum_{k=0}^{n-1}f(\theta_k)-\int_{-\pi/2}^{\pi/2}f(\theta)\,d\theta =-\frac{h^{2}}{24}\Bigl[f'\bigl(\tfrac{\pi}{2}\bigr)-f'\bigl(-\tfrac{\pi}{2}\bigr)\Bigr]+O(h^{4}) . \]

The slopes of \(f\) at the two poles are \(-1/(1+r)^2\) at the far pole and \(\pm1/(r-1)^2\) at the near pole, with the sign of \(r-1\). Dividing by the expected values of Eq. (9) gives the column h^2 estimate, computed by midpoint_error_estimate().

(13)
The printed error estimate DERIVED
\[ \delta(r)\approx\frac{h^{2}}{48}\,r^{2}\Bigl[\frac{1}{(r+1)^{2}}+\frac{1}{(r-1)^{2}}\Bigr]\quad(r>1),\qquad \frac{g_{\rm num}}{M}\approx\frac{h^{2}}{48}\Bigl[\frac{1}{(r+1)^{2}}-\frac{1}{(1-r)^{2}}\Bigr]\quad(r<1) . \]

At the centre the two terms cancel, and far away \(\delta\to h^2/24\), the mass error of Eq. (5). The estimate is a formula, not a sum over tiles, so its agreement with the printed error is a real check on the sum. Its \(1/(r-1)^2\) term, from the pole nearest the test mass, grows without limit as \(r\) approaches the shell, which is where Beat 5 goes.

Experiments that go with this beat: Experiment 4 in Suggested Experiments.

Beat 5 · The surface is hard

Go close to the shell, half a hundredth of a radius inside and outside it, and a little farther out, first with the default 100 divisions and then with 10000. The second run takes about ten seconds, like the second run of Beat 4.

python main.py --radii 0.995 1.005 1.01 1.05 1.1
python main.py --nDiv 10000 --radii 0.995 1.005 1.01 1.05 1.1

Look at latitude step h = pi/nDiv, at predicted g and relative difference, and at h^2 estimate and the * marks beside it.

Three tasks, in order. First, the default run. Just inside, at 0.995, g/M is 0.15216, a leftover pull of 0.15 times the mass where there should be none, and just outside, at 1.005, the relative difference is -0.15117, a 15% error; the estimates, -0.82246 and 0.83072, do not even have the right signs. They are marked *, and so are those at 1.01 and 1.05; only at 1.1 do the error, 0.0025682, and the estimate, 0.0024936, agree. Then the fine run. Now nothing is marked, and the estimates agree with the errors at every radius: -8.2331e-05 against -8.2246e-05 at 0.995, and 8.3158e-05 against 8.3072e-05 at 1.005. A row without a mark is not a guarantee, though: just past the marking threshold, with 1257 divisions, the estimate at 1.005 is still about 8% off (Experiment 7). Then read the jump. In the fine run predicted g goes from -1.0346e-06 inside to 0.012443 outside, a jump of 0.012444 across a hundredth of a radius, against the expected 0.012442. Say why the tiles must be small compared with the distance to the shell before the sum can be trusted there.

Then the condition. Near the shell the test mass is within \(|r-1|\) of the nearest tiles, and their pull changes completely over that distance. Eq. (12) is a series in powers of \(h\) measured against the scale on which \(f\) changes, which is the shell radius 1 far from the shell and \(|r-1|\) near it, so the estimate, and the sum, can be trusted only when \(h=\pi/n\ll\min(1,\ |r-1|)\). With 100 divisions \(h=0.031416\), more than six times the distance 0.005, so each tile near the pole is larger than its distance from the test mass, and the sum is poor. With 10000 divisions \(h=0.00031416\), a sixteenth of that distance. The program turns the condition into a rule for its marks.

(14)
The marking rule ALGORITHM
\[ h\ \ge\ \tfrac12\min\bigl(1,\ |r-1|\bigr)\quad\Longrightarrow\quad\text{row marked }*. \]

A marked estimate is unreliable, although the sum itself may happen to be close; the factor \(\tfrac12\) is a choice, and an unmarked estimate close to the threshold can still be off by several per cent. The exact field does not just become hard to compute at the shell: it jumps.

(15)
The jump across the shell DERIVED
\[ g(1^{+})-g(1^{-})=\frac{GM}{R^{2}}-0=4\pi G\varepsilon . \]

The jump is \(4\pi G\) times the mass per unit area \(\varepsilon\), whatever the shape of a surface layer; it is the reason the program does not evaluate the field at \(r=1\) itself, and why the plot has a gap there. Across the pair 0.995 and 1.005 the expected change is \(M/1.005^2=0.012442\), the jump less the small fall-off of the outer field. Beat 6 turns to the plot.

Beat 6 · The relative-difference plot

Run the program with all its defaults. The plot now shows the relative difference, not the pull.

python main.py

Look at the plot and at the scale of its vertical axis, and at the rows 0.995, 1.005 and 5 of the table.

Three tasks, in order. First, the scale. The curve runs from about -0.15 to about +0.15, set by the two spikes on either side of the dashed line, which are the 15% errors of Beat 5 (0.15216 and -0.15117 in the table). Then everywhere else. On this scale the curve lies on zero from the centre to within a few hundredths of the shell, and from just outside the shell to r = 4.995: the errors of Beats 2 to 4 are far too small to see. Then compare the definitions. At r = 5 the table prints 4.6409e-05, most of which, 4.1125e-05, is the mass error; the plotted value just inside r = 5 is only about 5.3e-06, because the plot divides by the tiles' own mass. Say which of the two relative differences measures only the error in the shape of the field.

Then what is plotted.

(16)
The plotted relative difference DEFINITION
\[ \delta_{\rm plot}(r)=\frac{g_{\rm num}(r)-M_{\rm num}/r^{2}}{M_{\rm num}/r^{2}}\quad(r>1),\qquad \frac{g_{\rm num}(r)}{M_{\rm num}}\quad(r<1) . \]

This is the table's comparison, Eq. (9), with the tiles' mass \(M_{\rm num}\) in place of the exact mass \(M\). It is computed at the plot's 1000 radii from 0 to 4.995, except \(r=1\), by compute_acceleration_profile(). The two definitions are simply related, but differently outside and inside, because outside the mass also sets the expected pull.

(17)
The two relative differences DERIVED
\[ 1+\delta_{\rm plot}=\frac{1+\delta}{M_{\rm num}/M}\quad(r>1),\qquad \delta_{\rm plot}=\frac{\delta}{M_{\rm num}/M}\quad(r<1) ; \] \[ \delta_{\rm plot}\approx\delta-\frac{h^{2}}{24}\quad(r>1),\qquad \delta_{\rm plot}\approx\delta\left(1-\frac{h^{2}}{24}\right)\quad(r<1) . \]

The second line keeps only the first power of \(h^2\), using \(M_{\rm num}/M\approx1+h^2/24\) from Eq. (5); outside it also drops the product \(\delta\,h^2/24\), which is smaller still. With the table's values at \(r=5\), \((1+4.6409\times10^{-5})/(1+4.1125\times10^{-5})-1=5.3\times10^{-6}\): far away \(\delta\) tends to the mass error and \(\delta_{\rm plot}\) tends to zero. Inside the shell the two differ only by the factor \(M/M_{\rm num}\): at \(r=0.5\) the table's g/M of -7.3167e-05 becomes -7.3164e-05 in the plot, too little a change to see. The exterior formula must not be used inside: it would subtract the mass error from a quantity that does not contain it, and give -1.1429e-04. Beat 7 changes the mass.

Beat 7 · Epsilon only sets the scale

Double the shell's mass per unit area and plot the pull again.

python main.py --epsilon 0.002 --outputType acceleration

Look at the mass lines, at predicted g and expected g, and at relative difference, and compare them with Beat 0.

Three tasks, in order. First, the masses: 0.025134 and 0.025133, twice those of Beat 0, with the same relative difference, 4.1125e-05. Then the pulls: 0.0062838 at r = 2, twice the 0.0031419 of Beat 0, and the plot has the same shape with twice the height. Then the comparisons: 9.1423e-05 at r = 2 and g/M = -7.3167e-05 at 0.5, exactly as in Beat 0. Say why no relative difference can depend on --epsilon.

Then the scaling. Every tile mass in Eq. (4) is proportional to \(\varepsilon\), so the sum, the exact mass and the exact field all are.

(18)
Scaling with the mass per unit area DERIVED
\[ g_{\rm num}\propto\varepsilon,\qquad M\propto\varepsilon,\qquad \delta,\ \ \frac{g_{\rm num}}{M},\ \ \frac{M_{\rm num}}{M}\ \ \text{independent of }\varepsilon . \]

\(\varepsilon\) is described as the shell's thickness over its radius because a shell of density 1 and thickness \(\varepsilon\) has mass \(\varepsilon\) per unit area. The tiles all lie on the radius-1 sphere whatever \(\varepsilon\) is, so it does not make the shell thicker. It sets the size of the jump of Eq. (15) and nothing else about the shape of the field. Beat 8 goes to the coarsest tilings and to inputs the program refuses.

Beat 8 · Coarse tilings and the hard cases

Use the coarsest possible tiling, a single ring, and then try a comparison radius on the shell and more divisions than the program allows. The last two commands are rejected; the messages say why.

python main.py --nDiv 1
python main.py --radii 1
python main.py --nDiv 100001

Look, in the first run, at the mass relative difference, at the whole table and its * marks, and at the plot. Then read the two error messages.

Three tasks, in order. First, the mass: the single ring, at the equator, carries 0.019739 against the shell's 0.012566, a relative difference of 0.5708, which is \(\pi/2-1\) from Eq. (5) with \(h=\pi\). Then the field: inside the shell g/M is 0.56199 at r = 0.5, a strong pull towards the ring's plane, and outside the relative difference rises from 0.12397 at r = 2 to 0.48105 at 5, on its way to the mass error 0.5708 of Eq. (10); every estimate is marked *. Then the errors: --radii 1 is refused because the field is discontinuous at the shell, and --nDiv 100001 because the program limits the divisions to 100000. Say why a single ring pulls like the whole shell only when the test mass is far away.

Then the rules of the calculation that set these limits.

(19)
Radii, divisions and the omitted surface ALGORITHM
\[ r_j=0.005\,j,\quad j=0,1,\dots,999,\ j\ne200;\qquad 1\le n\le100\,000;\qquad 0\le r_{\rm table}\le10^{100},\ \ r_{\rm table}\ne1 . \]

The plot uses the grid \(r_j\), from 0 to 4.995, and skips \(j=200\), which is \(r=1\); the returned profile keeps a value of 0 there as a placeholder, and the plot leaves a gap. The table, --radii, may use any radius from 0 to \(10^{100}\) except 1, including radii far beyond the plot, and --epsilon must lie between \(10^{-100}\) and \(10^{100}\); these ranges keep every printed result within the range of the computer's floating-point arithmetic. The limit on \(n\) keeps the run time and memory reasonable: the plotted profile adds \(n\) rings at each of 1000 radii, so its time grows in proportion to \(n\). The program treats each latitude as a uniform ring, whatever \(n\) is, so even with one division the ring's sideways pulls are taken to cancel. Other rejected inputs are listed under Parameters.

Experiments that go with this beat: Experiment 9 and Experiment 11 in Suggested Experiments.

Algorithm

This section collects in one place the rules of the calculation that the beats introduced one at a time.

Printed summary

  1. Compute the tiles' mass \(M_{\rm num}\) of Eq. (4) and the exact mass \(M=4\pi\varepsilon\), and print them with their relative difference.
  2. For each comparison radius (--radii), add the ring pulls of Eqs. (6) to (8), starting at the ring nearest the south pole and moving northwards.
  3. Print the sum, the expected pull of Eq. (2), the comparison of Eq. (9) and the estimate of Eq. (13), with a * where the condition of Eq. (14) fails.

Plotted profile

  1. Compute \(M_{\rm num}\) as above.
  2. For each radius \(r_j=0.005\,j\), \(j=0,\dots,999\), except \(r=1\), add the ring pulls as for the table. Leave the value at \(r=1\) at the placeholder 0.
  3. For the relative-difference plot, convert each value with Eq. (16).
  4. Draw the curve with a gap at \(r=1\) and a dashed line at the shell.

Two implementations of the profile

The default compute_acceleration_profile_textbook() uses plain nested loops, over radii and then over rings, so that each step of the sum can be read. The alternative compute_acceleration_profile_optimized() computes the ring geometry once and adds the rings with NumPy arrays, a few radii at a time so that no array becomes too large; it gives the same values to rounding and is much faster. Near the end of physics_spheregravity.py two lines choose between them:

compute_acceleration_profile = compute_acceleration_profile_textbook
# compute_acceleration_profile = compute_acceleration_profile_optimized

Swapping the comment mark between them selects the other one; the two functions have identical signatures and return values, so nothing else needs to change. The printed table always uses compute_acceleration_at_radii(), which follows the textbook loop.

Program Files

main.py
Entry Point & Configuration

Defines every command-line option in build_parser(), calls the driver for the plotted profile, prints the summary (see Printed Summary) with print_comparison(), and passes the profile to the plotter. It can be imported without running anything.

physics_spheregravity.py
Physics Layer

Contains the constants, compute_shell_mass() and compute_continuum_shell_mass(), compute_acceleration_at_radii() for the table, midpoint_error_estimate(), the two profile implementations and the line that selects one of them as compute_acceleration_profile(), the input checks, and the version and build identifier.

driver_spheregravity.py
Driver Layer

Provides run_spheregravity(nDiv=100, outputType='acceleration', epsilon=0.001), which returns the plotted radii and values as two NumPy arrays, and get_version_info().

plot_spheregravity.py
Visualisation

Provides plot_spheregravity(radius, acceleration, outputType='acceleration'), which checks the arrays, draws the profile (see Plot), shows it, and returns the figure and axes so that a script can save them.

Quick Start

Requirements

Python 3.10 or later with numpy and matplotlib:

pip install numpy "matplotlib>=3.5"

Running the Program

Clone or download the repository, then open a terminal in the folder that contains main.py:

cd GFTGU-Programs/SphereGravity
python main.py
python main.py --outputType acceleration
python main.py --help

To display the program version and build identifier without running a calculation, use python main.py --version. Options omitted from a command keep their defaults.

# A finer tiling, and the comparison at radii of your choice
python main.py --nDiv 1000 --radii 1.1 1.05 1.01

Command-Line Parameters

All settings are command-line options described in main.py. --outputType changes only the plot, and --radii only the printed table.

ParameterDefaultDescription
--nDiv100Divisions \(n\) in latitude and in longitude, Eq. (3); a whole number from 1 to 100000. The plotted profile takes a time proportional to it.
--outputTyperelative_differenceacceleration plots \(g_{\rm num}\); relative_difference plots Eq. (16).
--epsilon0.001Mass per unit area \(\varepsilon\), from \(10^{-100}\) to \(10^{100}\); it scales every pull and mass, Eq. (18).
--radii0.5 0.995 1.005 2 3 4 5Radii of the printed comparison, Eq. (9); each not negative, not 1 and at most \(10^{100}\).
Input checking: The command-line parser rejects a --nDiv that is not a whole number from 1 to 100000, an --epsilon outside \(10^{-100}\) to \(10^{100}\), an unknown --outputType (the underscore in relative_difference is required), and a --radii value that is not a number, is negative, is exactly 1 or exceeds \(10^{100}\). These ranges keep every printed result within the range of double-precision numbers, so that no printed result underflows to zero or overflows. The physics functions make the same checks when they are called from a script.

Plot

The plot draws the profile from \(r=0\) to 4.995 against the radius in shell radii, with a red dashed line at the shell, \(r=1\), and a gap in the curve there. With --outputType acceleration the vertical axis is the pull \(g_{\rm num}\), positive towards the centre; with relative_difference it is the relative difference of Eq. (16), whose range is usually set by the spikes beside the shell. plot_spheregravity() returns the figure and its axes, so a script can save the plot with figure.savefig().

Suggested Experiments

The experiments are ranked from introductory to advanced, and each is cited by the beat it extends. Each command is run from the program's folder.

1 · See the Theorem — Introductory

Plot the pull with the default tiling and with ten times as many divisions. Check that it is essentially zero inside and falls as \(1/r^2\) outside, and look at how the small wiggles on either side of the shell change.

python main.py --outputType acceleration
python main.py --nDiv 1000 --outputType acceleration

2 · The Inverse-Square Law from the Table — Introductory

Print the comparison at radii that double each time. Divide each predicted g by the next one and check that the ratio is close to 4; then say how close it should be, using the relative difference column, and why the five printed digits cannot show the departure for the most distant pair.

python main.py --radii 1.5 3 6 12 24

3 · The Mass of the Tiles — Introductory to Intermediate

Run a few coarse tilings and compare the printed mass relative difference with \((h/2)/\sin(h/2)-1\) of Eq. (5), computed on a calculator from the printed \(h\), and with \(h^2/24\). How coarse must the tiling be before the two formulas differ in the second digit?

python main.py --nDiv 3
python main.py --nDiv 30
python main.py --nDiv 300

4 · Schutz's Convergence Test at r = 1.1 — Intermediate

Print the comparison at \(r=1.1\) for 100, 1000 and 10000 divisions. The relative differences are about \(2.6\times10^{-3}\), \(2.5\times10^{-5}\) and \(2.5\times10^{-7}\): each tenfold refinement gives a hundredfold improvement. Compare each with h^2 estimate, and say why a statement about convergence must compare errors at the same radius.

python main.py --radii 1.1
python main.py --nDiv 1000 --radii 1.1
python main.py --nDiv 10000 --radii 1.1

5 · Map the Interior — Intermediate

Print g/M at many interior radii and plot it by hand against \(r\), with the estimate beside it. Where does the first * appear, and how well does the estimate do just before it?

python main.py --radii 0.1 0.3 0.5 0.7 0.9 0.95 0.98

6 · Read and Save the Plotted Profile — Intermediate Programming

The driver returns the plotted radii and values as two arrays, on the grid \(r_j=0.005\,j\), so a radius on that grid is found from its index. Run this script from the program's folder. It prints the plotted relative difference of Eq. (16) at three radii; compare the value at \(r=2\) with the table's 9.1423e-05 of Beat 2 through Eq. (17). Then extend it: after from plot_spheregravity import plot_spheregravity, plot_spheregravity(radius, accel, outputType="relative difference") returns the figure and axes, and figure.savefig("profile.png") saves the plot once its window is closed.

from driver_spheregravity import run_spheregravity

radius, accel = run_spheregravity(nDiv=100, outputType="relative difference")
for r in (1.1, 2.0, 4.995):
    i = round(r / 0.005)
    print(radius[i], accel[i])

7 · How Fine Near the Shell? — Intermediate to Advanced

Find the smallest number of divisions for which the row at \(r=1.005\) loses its *, first from Eq. (14) and the marking rule, then by running the program on either side of it. Compare the error with the estimate in both runs, and then at ten times that number of divisions.

python main.py --nDiv 1256 --radii 1.005
python main.py --nDiv 1257 --radii 1.005

8 · Measure the Jump — Intermediate to Advanced

Print the pull a hundredth of a radius inside and outside the shell with fine tiles, for two values of \(\varepsilon\). Compare the difference of the two predicted g values with \(4\pi\varepsilon/1.01^2\), the jump of Eq. (15) less the fall-off of the outer field, and check that it doubles with \(\varepsilon\). Then move the two radii closer to the shell: where does the error of the sum, shown by h^2 estimate, become larger than the fall-off correction?

python main.py --nDiv 10000 --radii 0.99 1.01
python main.py --nDiv 10000 --epsilon 0.002 --radii 0.99 1.01

9 · Coarse Tilings — Advanced

With very few divisions the tiled shell is far from spherical. Print the comparison far from the shell for one, two and three divisions and check that the relative difference approaches the mass error, Eq. (10), in every case. Then look at the plots: for which tilings does the interior still look like a hollow shell?

python main.py --nDiv 1 --radii 10 100 1000
python main.py --nDiv 2 --radii 10 100 1000
python main.py --nDiv 3 --radii 10 100 1000

10 · Replace the Sphere by an Ellipsoidal Homoeoid — Advanced Programming

In a separate copy of the program, replace the spherical shell by a thin ellipsoidal shell of the kind called a homoeoid: the material between two similar, concentric, similarly oriented ellipsoids of uniform density. Deforming the spherical coordinates while keeping the spherical tile masses is not enough; derive the correct mass of each tile and compute every component of the pull, including at points off the symmetry axis. Check that the pull inside tends to zero as the tiling is refined, while the pull outside depends on direction and so cannot be that of a point mass.

11 · NumPy Vectorization and Computational Tradeoffs — Advanced Programming

Compare compute_acceleration_profile_textbook() with compute_acceleration_profile_optimized(). Identify which loops the NumPy array operations replace and how the ring geometry is computed once and reused. Select each in turn with the two lines described under Algorithm, check that they give the same profile in both output modes, time them for several values of --nDiv, and explain why the optimized version works through the radii in bounded chunks rather than building one array for every radius and ring. Which is better for learning the method, and which for large calculations?
